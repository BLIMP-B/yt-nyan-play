# 不安定な回線での音声（v0.5.23）

「設定」→「音声の通信環境」で選び、保存します。既存の設定にも「不安定な回線」を初期値として追加します。ビットレートは48 kbpsを初期値に、16〜384 kbpsの整数で指定できます。プリセット選択時は48 / 96 / 128 kbpsを入力し、その後個別に変更できます。接続中のDiscord送信にも反映し、読み上げ・メディア・時報に共通で使います。

| 通信環境 | Discord音声 | VC受信バッファ | Discordメディア・BGMのIPCバッファ | PC通話モニターの追加バッファ |
|---|---:|---:|---:|---:|
| 不安定な回線（初期設定） | 48 kbps | 240 ms | 600 ms | 120 ms |
| 通常の回線 | 96 kbps | 120 ms | 300 ms | 80 ms |
| 安定した回線 | 128 kbps | 80 ms | 160 ms | 80 ms |

送信は48 kHzステレオ・20 msごとのOpusです。初期値では音声部分が1パケット120バイトで、音の大きさによる通信量の急増を抑えます。UDP・暗号化などを含む目安は1接続あたり約70〜80 kbpsです。複数サーバーのVCへ送る場合は接続数に応じて増えます。ステレオと静かな音を維持し、無音も連続送信します。v0.5.12ではFECと符号器の想定損失率を0にしました。同梱libopusでFEC有効・想定損失率20％を指定すると48 kbpsのステレオ波形が大きく崩れることを、独立したFFmpegデコーダーで再現したためです。欠落時のOpus補間は受信側に委ねます。受信バッファの不安定回線設定と48 kbpsの初期値は維持します。

メディアとBGMの供給時計がDiscordの送信時計と少しずれる場合は、バッファの平均残量に応じて読み出すサンプル数を補間し、最大±0.5％の範囲でゆっくり補正します。20 msを丸ごと繰り返したり捨てたりせず、継続的なバッファ枯渇と再充填待ちを避けます。実際に音源が止まった場合は不足として記録します。読み上げと正時の時報音はこの速度補正を通しません。診断JSONには実際の符号化設定、媒体別の残量・補正比率・不足回数・過剰な滞留で捨てたサンプル数も出力します。

音声形式の取得は、初回のツール導入を最大120秒、導入後のCookie取得・形式解析を別枠で最大20秒待機します。停止・次の要求では待機を中断します。共有する導入処理は次回用に完了できます。ブラウザ側の読み込み・ログインの時間は別です。

受信バッファは最大1秒、PC側は最大0.5秒です。長い滞留は古い音声を捨てて遅延の増加を防ぎます。短い欠落は最大40 msの減衰した直前音で補い、その後は無音にします。音声が戻ると最大120 msの待機で再開します。プロファイル変更後のPC追加バッファは次のモニター開始時に反映します。送信側ミキサーのバッファはメディアだけに適用し、読み上げや正時に合わせた時報を待たせません。

メディア取得は従来どおり、各サービスの最も低いビットレートの音声配信を優先し、なければ最低画質を選択します。FFmpegからアプリへの96 kbps配信はPC内のループバックで、インターネットへの送信帯域ではありません。FFmpeg側で再生位置を適用済みの音声ストリームはブラウザ側で再シークせず、同じ配信URLの再読み込みを防ぎます。音声取得とDiscord送信を同時に行うため、回線全体には取得元の配信帯域も必要です。

OpusScriptのJavaScriptラッパーにあるバイトポインターと16ビット配列のずれ、および最大120 msのパケットに不足する領域を避け、同じlibopus WASMに正しい境界の領域を渡します。デコーダーは一度だけ終了し、古い受信ストリームの遅延したエラーが新しい受信を終了しないようにしました。

自動試験では実Opusの120 msパケット・32人の同時受信と再購読、180 msの遅延変動、約9％の欠落、80 kbpsの帯域モデルを使います。実Discordのインターネット経路・利用者のスピーカーまでの確認にはBotを参加させた実機確認が必要です。

## メディアの開始時とDiscord送信の対策

アプリが変換する音声ストリームは、再生用の4 / 2 / 1秒に、Chromiumがまだデコードせずに保持する部分への余裕3秒を加え、計7 / 5 / 4秒を先読みします。変換したOggのサンプル時計を読み、再生位置から9 / 7 / 6秒先までを配信側で管理します。PC内のOggは96 kbps固定とし、静かな音源でバイト単位の読み込み待ちが長くなることを防ぎます。インターネットからの取得形式とDiscord送信の48 kbps初期値は別です。ブラウザが非シーク音声のTimeRangesをEOFまで返さない場合も、先読み待機を続けません。再生中に供給が尽きた場合は再び蓄えてから再開します。短い音源は残りの長さに合わせ、長さ不明の短いストリームも変換完了を使って待機を解きます。無音や小音量を見て再生を止める処理ではありません。

サイト内ブラウザ再生では、長さが分かるメディアの開始前に先読みを試みます。サイトが一時停止中の取得を止める場合は最大8秒で待機を解き、サイト自身の再生制御に戻します。ライブや再生開始後に長さが判明した媒体を途中から止めず、広告の時間も先読み待機へ混ぜません。

Discordへの送信は、音声データの供給バッファとパケットの送信時刻を別々に管理します。初期設定の600 msは、アプリ側のIPCが500 ms止まる場合を想定した値です。メディアとBGMに適用し、通常の読み上げと正時の時報音にはこの待機を加えません。PCとの間にはその分の遅れが加わります。自然終了時は末尾と最後の部分フレームまで送り、停止・次の要求では排出待ちを中断します。

送信時計が遅れた際、過去の20 msの周期を1 ms間隔で取り戻す集中送信を抑えます。通常は20 ms、滞留を戻す間も18 ms以上の間隔を設けます。raw Opusを待機させ、実際に送る直前に既存のDiscord実装でRTPヘッダーと暗号化を行います。接続ごとに最大50フレームを上限とし、過負荷で捨てた場合は診断に記録します。再接続や停止時には古い内容を解放します。

診断は「先読み不足」（再生ページ）、「音声供給不足」（Discordミキサー）、「送信遅延・まとめ送り・送信待ち破棄」（送信時計）を区別します。送信処理自身を強制停止した時間や、インターネット・受信側の遅延を消せることは意味しません。

`scripts/verify-audio.mjs`は前半に1.4 / 2.8 / 3.6秒と長くなるHTTP供給停止を入れ、旧方式と修正後のPC出力を比較します。`npm run verify:voice-impairments`は3つのVCを模した独立UDP受信で、500 msのIPC停止と70 msの送信処理停止を別に与えます。後者は各VC 80 kbps・短いバースト許容量の帯域モデルも通します。これは実Discordへのログイン・DAVE・利用者のスピーカー・60分試験を代替しません。
