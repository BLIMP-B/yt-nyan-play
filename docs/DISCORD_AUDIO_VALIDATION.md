# Discord音声の実通話検証

にゃんとーくv0.5.11ではファイル種類・絵文字・スタンプの読み方、PCへのメディア/BGM出力と長時間通話の診断を修正・追加する。実Discordの受信側で「音途切れが観測上1時間に1回程度」という条件は、実通話の測定を完了するまで未達成として扱う。

## 2026年10月12日の返却結果

別環境でv0.5.11の配布EXEのSHA256を照合し、利用者本人がDiscord受信を聴取した。PC読み上げ・YouTube・VC不在時のPC継続、添付種類、教育・無音・忘却、再生モード・停止優先・共通時報は試した条件で確認済み。録音・WebRTC受信統計は取得されていない。

Discord音声は不合格。不安定回線/48 kbpsは強いノイズで音楽として聴取できず、安定回線/128 kbpsでも短い無音が残った。二重受信を解消した後も症状が残った。最終の48 kbps試行は要求から停止まで265.116秒で打ち切られ、実音声の観測時間と途切れ件数は不明。60分の第一区間も第二区間も完了していない。送信側の遅延0件・まとめ送り13件・音声不足1件は、受信側の途切れ件数ではない。

未登録カスタム絵文字eraiの英字読み、ニコニコ要求から取得時間超過まで約95秒、SLM生成時間超過も報告された。長文中の無音候補は同文の再試験では再現しなかった。生成文/BGMが無効な設定での共通時報の合格を、生成文/BGM・正時同期・フェード秒数の合格へ拡張しない。

v0.5.12は符号化設定を修正し、独立FFmpegデコーダーで48/96/128 kbpsの左右波形と小音量を照合する。メディア/BGMの時計差補正は±0.25％の速度差を与えた各3分のシミュレーションで検証する。これらは実通話の長時間試験を代替しない。絵文字については、ネイティブ辞書にある未使用の「別文字→E/A」等の行が無関係な名前のローマ字変換を抑制しないよう、当該処理段階の入力に辞書の対象が存在した場合だけ読み方を保護する。取得待ちは全段階を含め20秒でブラウザへ切り替える。

v0.5.11の検証とv0.5.12の開発は並行している。旧版の観測結果は現在の開発へ取り込み、すでに修正した経路の回帰も維持する。教育と専用設定の共有登録を含む今回の追加、依存関係、未確認事項、公開済みv0.5.12との境界は[反映記録](VERIFICATION_V0_5_11_TO_V0_5_12.md)で追跡する。

次の実通話試験はv0.5.12と新版の診断JSONを使い、プロファイルを固定して48/128 kbpsを比較する。音質が改善したことを本人聴取または受信録音で確認してから、同じ最終設定で60分×2を開始する。前版の途中試行と通算しない。個別のサーバーID・投稿内容を含む返却証拠は公開リポジトリへ登録しない。

## 再開に必要な環境

- ユーザーがログインでき、こちらからも操作・確認できる可視ブラウザ。
- Discordのログイン、Gateway、CDN、音声接続を許可したネットワーク。HTTPページだけでなくWebSocketと音声通信も必要。
- ユーザーが指定したテスト用サーバー・VC、修正版を実行するWindows PCとBotの接続。
- 人間のパスワード・2FA・CAPTCHAはブラウザで本人が入力する。認証情報をチャット・Git・ログ・配布物に保存しない。

2026年10月11日時点のクラウド環境はDiscordのHTTPS接続がプロキシの403で拒否され、TCPの許可先も空だった。ブラウザ操作ツールがなく、ページを開くUIツールもこのホストでは利用不可だった。このため実ログイン・実VC聴取・1時間測定は未開始。ローカルUDPや試験メディアの結果を実通話の合格へ置き換えない。

## 測るもの

受信側でBotの音を確認し、途切れを時刻付きで記録する。ブラウザで取得可能ならWebRTCの受信パケット、損失、jitter、concealedSamplesの差分も記録し、意図した無音・停止・フェード・自然終了と区別する。他の参加者の会話やチャット本文は診断記録に含めない。

送信側では接続ごとに送信間隔、60msを超える間隔、5ms未満のまとめ送り、再生中のメディア/BGMバッファ不足を1分ごとにイベントログへ記録する。接続が切れた時間は送信間隔の計算から除外する。イベントログ右上のダウンロードアイコンから、認証情報やチャット本文を含めず診断JSONを保存できる。

送信診断は受信側の音途切れを直接測ったものではない。短い遅延がすべて聞こえるとは限らず、送信側が正常でも回線・受信側で途切れる可能性がある。

## 実行と判定

1. 通信環境「不安定」、Opusの初期値48kbps、実際のPC/Discord両方の出力で開始する。設定変更は記録する。
2. 動画音声を連続再生し、読み上げの割り込み、時報とBGM、履歴取得、Androidの動作も交ぜて少なくとも60分測定する。
3. 受信側で聞こえた途切れを記録し、送信診断・受信統計と時刻を照合する。連続した同一の途切れは一つの発生として数え、集計ルールを変更した場合は記録する。
4. 60分の実測で音途切れが2回以上あれば原因を修正し、修正後の新しい測定を開始する。1回以下になってから、次の60分でも確認する。負荷試験や無音状態だけで合格しない。
5. 検証結果には対象バージョン、送受信環境、実測開始/終了、音声が流れていた時間、発生時刻、変更した設定と未確認事項を残す。

接続待ちの間は、PC出力をメディアごとに測る試験と実ワーカー/Opus/UDPの負荷試験を続ける。YouTube検索・モデルの内容を試験用に置き換えたBGM試験は、その範囲を明記する。
